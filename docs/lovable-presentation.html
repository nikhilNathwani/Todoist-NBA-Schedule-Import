01 · Origin Story

Context

  • I use Todoist as the single place I plan my day — work, errands, everything.
  • I'm a Boston Celtics fan. I watch every game I can.
  • If "watch the Celtics game" isn't sitting next to everything else I'm planning that day, I forget to plan around it.
  • I need a Todoist task for each Celtics game.
Keep this concrete and personal — this is the "why," not a feature list. The whole project starts from a genuinely mundane annoyance, which is exactly what the next slide gets into.
01 · Origin Story

Problem

An 82-game season means 82 tasks. Typed. By. Hand.

  1. Look up the schedule
  2. Switch to Todoist
  3. Create task "Celtics vs. [Opponent]"
  4. Set the right date and time
  5. Go back to the schedule
  6. Repeat for all 82 games

Tedious, error-prone, and repeated every year 😩

This is the friction that motivated everything else. Nothing technical yet — just: this is annoying enough, ~80 times a year, that automating it is obviously worth it.
01 · Origin Story

A Solution

Quick-and-dirty Python script:

  • Scrapes the season schedule once
  • Uses my own hard-coded Todoist API token — no login flow, no other users
  • Creates a "Celtics schedule" project with 82 tasks, one per game
  • Runs in 30–60 seconds, once a year
$ python import_schedule.py
Scraping Celtics 2025-26 schedule...
Found 82 games.
Creating Todoist project "Celtics schedule"...
Adding 82 tasks...
Done in 41s.

This solved my problem 🙂. But why keep it to myself?

This existed purely for me — no OAuth, no frontend, no other users, just my own hardcoded API token. Frame this as "solved my own problem" before the next slide reframes the ambition.

04 · Technical Decisions

There's no free NBA schedule API.

What I looked for

  • A free public API covering all 30 teams' schedules
  • Searched — nothing usable existed
  • The NBA's own stats API isn't public, and third-party wrappers were incomplete or unreliable

What I built instead

  • Kept scraping CBSSports.com — the same source the personal script already used
  • Extended the scraper with Selenium (WebDriver) to navigate and pull every team's schedule, not just one
  • Scraping live on every request wasn't viable — the schedule only changes once a year
The real question wasn't "scrape or use an API." It was "scrape once and cache, or scrape on every visit" — exactly the storage question the next slide answers.
This is the twist that pays off the "NBA Schedule API" box from the system-diagram build — it doesn't exist. Bridges directly into the JSON-vs-database slide: now that scraping is expensive and infrequent, where do the results live between scrapes?
04 · Technical Decisions

Why a JSON file, not a database.

What the data actually needs

  • Read-only at request time — never written to during a request
  • Updated once a year, via a batch pipeline, not live traffic
  • ~400KB — small enough to fit trivially in memory

What a database would add

  • Write-consistency machinery this data never uses
  • Query infrastructure for a dataset simple enough to JSON.parse
  • Operational overhead with no corresponding benefit here
Not a shortcut — a fit. I'd reconsider this the moment the data needs runtime writes: live in-season score updates, or letting users customize their own schedule. Neither is true today.
This is a "know when NOT to reach for a tool" story — good judgment signal. Straight from the project's own README, not reconstructed after the fact. 04 · Technical Decisions

Vanilla JS + Express — and where it started to strain.

What it did well

  • Four pages, one form — genuinely small
  • Zero build step, nothing to configure
  • Right-sized for the scope, not under-engineered

Where the seams showed

  • Passing server data into templates felt like hand-rolling props
  • 9 vanilla scripts coordinating through global variables and code comments, not imports
  • A form's submit → loading → result flow spread across manual DOM writes
  • Hand-timed CSS transitions instead of real completion events
Be fair to the original choice here — it wasn't wrong for its scope. The point is specific, concrete friction, not "vanilla JS bad." Each bullet on the right maps to a real file you can cite if asked.
04 · Technical Decisions

Rebuilt in Next.js + React + TypeScript.

What it actually fixed

  • Data-fetching and rendering colocated — real typed props, not string-building
  • One component owns form state instead of globals shared by comment convention
  • Server Actions replace a hand-rolled fetch + JSON-parsing + error-shape check
  • Real DOM events (onTransitionEnd) instead of guessed timers

Told honestly

  • Fewer files (27→21), but comparable total lines — better organized, not shorter
  • One real framework limitation hit: a page component can't set a custom HTTP status
  • A full rewrite re-touches the most security-sensitive code — done on a branch, verified end-to-end before trusting it
This is where "evaluated multiple approaches" is strongest — you can go deep here if asked. Good place to mention the ISR-vs-SSG catch on the landing page if there's time: considered pure static generation, realized it would silently freeze a date-dependent value past the season boundary, used incremental regeneration instead.
04 · Technical Decisions

Cookie sessions — one of three real options.

In-memory

Simple, but wiped on restart and doesn't scale across instances.

Cookie-based ✓

No server-side storage. Each login is independent — nothing to persist. One token fits well inside the ~4KB limit.

Database-backed

Real persistence, but infrastructure this app's access pattern doesn't need.

How it's actually secured — not just "it's a cookie": httpOnly (blocks JS access), secure (HTTPS only), sameSite: lax, plus the access token itself is encrypted (not just signed) before it ever touches the cookie.
Land this as "I compared real alternatives and can defend the choice," not defensively. If pushed on security: the encryption is real authenticated encryption (confidentiality + tamper-detection), independently verified with a real decrypt-round-trip test.

05 · Key Challenges

The API couldn't tell me a user's project limit — so I asked.

  • I wanted to disable "Create New Project" before a user hit their cap, not after — a clean UX, not an error state
  • The Todoist API had no endpoint for a per-account project limit
  • I reached out to Todoist's Developer Relations team
  • Omar, their Customer Experience Developer & Advocate, confirmed: no direct way to query it — check isPremium instead, and hardcode the two tier caps (5 free / 300 premium)
  • I also passed along that a real limit-query endpoint would be a better long-term fix than every integration hardcoding numbers
"Check isPremium, and hardcode the caps — that's the accurate workaround today." — Omar, Todoist Developer Relations
Genuine collaborative-not-annoying framing: you asked a real question, got a real answer, and offered feedback constructively. Bonus, if asked "did anything change since": revisited this today and confirmed isPremium is directly queryable via getUser() — already using it correctly, the hardcoded caps are still the only real gap since the API still doesn't expose the numeric limits themselves.
05 · Key Challenges

A check that was right once, but not the second time.

The bug

  • The project-limit check ran once, right after login, and its result was baked into a URL parameter
  • The picker page just read that parameter — it never re-checked
  • Import a schedule as a new project, hit your cap, click "Import another" — the page still showed the stale, pre-import answer

The fix

  • Stopped passing the result through the URL entirely
  • The picker page now checks the live project count itself, every time it loads
  • Derived state that can go stale has to be recomputed at the point of use, not carried forward from when it was first computed
Real commit, May 7 2025: removed an isInboxDefault URL param computed once at OAuth callback, replaced with a fresh userReachedProjectLimit() check inside the picker route itself. Good "lesson that generalizes" line if asked: the exact same class of bug (trusting a value that can go stale) is worth watching for anywhere state crosses a request boundary.
05 · Key Challenges

The fewest steps a user has to take is zero extra steps.

Timezone conversion, without asking.

  • My scraper runs in my own timezone — the raw data needed a timezone to mean anything
  • First instinct: add a third input field, ask the user to pick theirs
  • But every extra decision is friction — I wanted zero, not one more field
  • Todoist stores due dates in UTC internally, and renders them in whichever timezone the viewing account is set to
  • So: convert each game's real local time to a true UTC instant during scraping — then Todoist displays it correctly for any user, automatically
scrape/formatDateTime.py
local_time = "7:30pm" (arena tz)
→ localize to arena timezone
→ convert to UTC
→ 2025-10-22T23:30:00Z
The insight isn't a Todoist trick — it's standard UTC-instant + client-side-local-rendering, the same pattern most calendar systems use. The point is recognizing you don't need to ask for information the receiving system already has.
